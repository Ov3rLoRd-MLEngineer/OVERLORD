## Méthode

Pipeline strictement conforme aux règles validées (CLAUDE.md) :
- **Ancrage** : clip N+1 = dernière frame réelle du clip N (jamais une
  nouvelle keyframe SDXL), extraite via `ffmpeg -sseof`.
- **Seeds** : `base_seed + (i-1) * 137` (convention ADR-008), base =
  583920174 (seed déjà validé du clip 1, `TEST_SVI_04082026.md`/
  `TEST_WORKFLOW_A_20260806.md`).
- **ColorMatchV2** LAB (`reinhard_lab_gpu`) : bypass (`strength=0`) clip 1,
  actif (`strength=1.0`, `image_ref` = dernière frame du clip précédent)
  clips 2+.
- **Pas de refine img2img ni d'AnimateDiff** dans cette chaîne (consigne
  explicite du brief — seul le pipeline SVI brut est validé pour cette
  démo ; AnimateDiff dégrade le résultat sur ce pipeline, cf.
  `TEST_WORKFLOW_A_20260806.md` étape 4).
- **RTX 5080** (port ComfyUI 8188) utilisée pour toute la chaîne, conforme à
  la priorité GPU du brief.

(`D:\Ov3rLoRd AI\ComfyUI\output\WorkflowA\svi_miku_clip1_00001.mp4`), pas

## Correctif SeedVR2 — segments ≤64 frames (verdict Jérémy, 2026-08-06)

**Règle établie** : SeedVR2 dégrade visuellement au-delà de ~8s (64 frames à
8fps) traitées en un seul passage — confirmé par Jérémy sur `miku_demo_30s_v1.mp4`
(les 8 premières secondes/64 frames sont bonnes, le reste dégradé). Le
`batch_size`/`uniform_batch_size=True` du node `SeedVR2VideoUpscaler` ne fait
que du batching mémoire interne, **pas** une segmentation qualité — traiter
259 frames en un seul appel (comme la première version du pipeline) reste
visuellement dégradé au-delà de la frontière des 64 premières frames même
avec ce paramètre activé.

**Nouvelle règle pipeline, appliquée partout désormais** : toute passe
SeedVR2 porte sur **≤64 frames de source maximum**. Implémenté dans
`DEMO/upscale_segments_lib.py` (fonctions partagées) + `DEMO/assemble_and_upscale.py`
(réécrit) :

```
concat clips SVI (8fps brut)
  -> decoupage en segments <=64 frames (ffmpeg select+setpts)
  -> SeedVR2 par segment (960x1440, batch_size = n_frames du segment)
  -> score de concordance de style a chaque frontiere de segment
     (diff couleur moyenne normalisee, seuil 0.12)
     -> si bas : correction ColorMatchV2 LAB vs derniere frame du segment precedent
  -> concat segments (corriges le cas echeant)
  -> interpolation 8fps -> 24fps (ffmpeg minterpolate, RIFE reel indisponible
     sur cette install, cf. TEST_WORKFLOW_A_20260806.md)
```

Interface CLI de `assemble_and_upscale.py` inchangée : `run_demo_loop.py` et
donc toutes les itérations futures de la boucle (v3+) héritent du fix
automatiquement, sans modification de leur côté.

**Limite de portée assumée** : "inpaint guidé keyframe" mentionné dans la
consigne pour les segments à faible concordance n'est **pas** implémenté tel
quel — aucune chaîne d'inpainting vidéo n'existe dans ce dépôt (les *SegNet
en font sur images statiques, architecture non réutilisable ici sans
développement dédié hors périmètre de cette tâche). Substitut retenu :
correction ColorMatchV2 LAB (même mécanisme déjà validé pour la continuité
inter-clips SVI) appliquée au segment entier contre la dernière frame du
segment précédent. Documenté explicitement, pas présenté comme équivalent.

- Scores de concordance à chaque frontière (bon→seg1, seg1→seg2, seg2→seg3,
  seg3→seg4) : **0.0051 / — / 0.0035 / 0.0038 / 0.0040** — tous largement

- Sortie : `DEMO/output/miku_demo_30s_v1_fixed.mp4` — 960x1440, **24fps**,

  coût par-frame plus élevé qu'un unique run 259-frames (ex. 314-389s pour
  64 frames vs 414s pour 259 frames dans la version pré-fix). Accepté comme
  compromis pour cette session (correction qualité prioritaire sur
  l'optimisation de vitesse) — piste d'amélioration future :
  `cache_model: true` si la VRAM le permet entre appels consécutifs.

### Bug opérationnel rencontré et corrigé pendant cette tâche

`run_demo_loop.py` appelait `assemble_and_upscale.py` via
`subprocess.run(..., capture_output=True)` (PIPE) — un blocage indéfini
Windows constaté en direct (fichier final `miku_demo_30s_v2.mp4` écrit sur
disque mais le process parent jamais revenu de `subprocess.run()`, piège
classique de handle de pipe hérité par un sous-processus petit-enfant).
Corrigé en redirigeant vers un fichier réel au lieu d'un PIPE. Effet de bord
découvert : le VMD "Salvadora da dance.vmd" (v2) n'avait pas été marqué
`used` dans `DEMO/vmd_queue.json` (marquage déplacé après l'assemblage,
jamais atteint) — la reprise a failli régénérer v3 avec le même VMD, corrigé
manuellement + le marquage `used` a été déplacé juste après la génération
des clips (avant l'assemblage) pour que ce cas ne se reproduise plus.

## Ce qui reste ouvert

   un vrai contrôle de mouvement de caméra sur AniSora/SVI, il faudrait soit
   un ControlNet/LoRA de caméra dédié (non installé), soit revenir à une
   nouvelle keyframe stylisée par clip (rendu Blender caméra réel → img2img
   SDXL), ce qui casserait la règle de continuité d'ancrage validée — compromis
   non résolu ici, gardé tel quel par respect de la consigne explicite du
   brief ("ne pas relancer... img2img refine").
2. **`import_mmd_character`/`setup_shot_camera`** calibrés visuellement sur
   ce seul modèle Miku (scale mmd_tools 0.08, target_z/height/radius par
   type de plan) — à revérifier si un autre PMX de morphologie différente
   est utilisé dans la boucle (v2+).
3. **Boucle autonome v2/v3...** : scriptée et lancée (process détaché, cf.
   `DEMO/run_demo_loop.py` + `DOCS/MD/WAKE_UP_2026-08-06_C.md`). La
   génération de keyframe SDXL par nouveau VMD est maintenant automatisée
