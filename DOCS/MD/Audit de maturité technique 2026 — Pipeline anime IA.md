# Audit de maturité technique 2026 — Pipeline anime IA "Ov3rLoRd" (Onibaku Gumi)

## TL;DR
- **Deux axes sont mûrs et prototypables immédiatement sur votre infra dual-GPU 16 Go : le QC anatomique automatisé** (HADM, DiffDoctor, HandRefiner — code et poids ouverts, détecteurs ViTDet/SegFormer légers qui tournent sur une seule carte) **et la vérification de conformité au design canonique ("DesignLock")** via similarité de features DINOv2/DINOv3 + matching bipartite, une technique désormais standard dans la littérature 2026 et directement branchable sur votre SAM fine-tuné existant.
- **Le stabilisateur de lineart pur ("anti-line-boiling") reste le gap le plus profond : il n'existe en 2026 aucun modèle dédié qui prenne une séquence de lineart tremblante et la stabilise.** Les solutions réelles contournent le problème (reformulation vectorielle SVG, inbetweening géométrique type AnimeInbet, ou ControlNet lineart + module temporel/VACE), toutes soit prototypes de recherche lents, soit orientées rendu final plutôt que couche de lignes.
- **Côté outils vidéo, la ligne de partage est nette : MatAnyone, SeedVR2, RIFE, blender-mcp, AniSora V3.2/Wan 2.2 TI2V-5B et VACE 1.3B sont réalistes sur 16 Go** (souvent avec quantification/offload), tandis que **VACE-Fun-A14B (≥80 Go officiel), Wan 2.2 A14B et ToonComposer (~57 Go VRAM) sont hors de portée sans datacenter ou cloud.** L'axe à prioriser pour un prototype court terme est le QC anatomique ; l'axe hors de portée immédiate est le lineart temporel de qualité production.

## Key Findings

1. **QC anatomique automatisé (Axe 1) — MÛR, prototypable.** Trois familles distinctes de la couche "génération" existent : (a) détecteurs d'artefacts humains post-génération avec poids ouverts (**HADM**, arXiv 2411.13842 ; **DiffDoctor**, ICCV 2025, arXiv 2501.12382) ; (b) détection+correction de mains (**HandRefiner** ACM MM 2024, **HandCraft**, **3D-mesh-guided refinement** arXiv 2506.12680) ; (c) scoring VLM (**ArtifactLens**). Ces détecteurs produisent des bounding boxes / cartes de confiance par pixel utilisables directement comme filtre de dataset.
2. **Stabilisateur de lineart pur (Axe 2) — GAP réel, immature.** Aucun modèle "lineart deflicker" dédié en 2026. Contournements : vectorisation (Sketch Video Synthesis 2311.15306, Live Sketch 2311.13608), inbetweening géométrique (AnimeInbet, ICCV 2023, arXiv 2309.16643), ou ControlNet lineart + module temporel (AnimateDiff/TemporalNet, VACE).
3. **ColorLock / cohérence de palette (Axe 3) — PARTIELLEMENT mûr.** Deux approches : conditionnement à la génération (**Palette-Adapter / Palette-Aligned Diffusion**, arXiv 2509.02000) et correction post-génération (**wavelet color correction**, training-free). Pas de "ColorLock" clé-en-main mais briques combinables.
4. **Outils vidéo (Axe 4) — statuts variés, voir tableau détaillé.** MatAnyone (CVPR 2025) et MatAnyone 2 (CVPR 2026) activement maintenus ; AniSora V3.2 (sept. 2025, finetune Wan 2.2) ; VACE (Wan 2.1 mûr, Wan 2.2 "Fun VACE" expérimental) ; Wan 2.2 TI2V-5B ; blender-mcp (écosystème très actif) ; RIFE (mûr, modèles anime v4.7-4.10) ; TLB-VFI (ICCV 2025) ; SeedVR2 (16 Go via BlockSwap).
5. **DesignLock / conformité topologique (Axe 5) — MÛR conceptuellement.** La vérification par similarité de features DINO (sDINO, DINO-I, matching bipartite Linear Sum Assignment restreint par classe SAM) est devenue standard 2026 (VIGIL 2602.14633, HECTOR 2603.08850, DivRL 2606.23950).
6. **Comparaison avec l'existant (Axe 6) : priorité au QC anatomique et au DesignLock** (réutilisent votre SAM + VLM Qwen déjà en place) ; **hors de portée immédiate : le lineart temporel production et VACE 14B.**

## Details

### Axe 1 — QC anatomique automatisé (détection/scoring post-génération)

**État de maturité 2026 : mûr.** Le pipeline utilise déjà des LoRA "anti-mains-difformes" (prévention à la génération). L'axe demandé — détection/scoring *après* génération pour filtrer un dataset — est couvert par plusieurs travaux avec code et poids ouverts.

- **HADM (Human Artifact Detection Models)** — "Detecting Human Artifacts from Text-to-Image Models", Kaihong Wang et al., arXiv 2411.13842 (v1 nov. 2024, v2 mars 2025). Code et poids : github.com/wangkaihong/HADM. Deux modèles : **HADM-L** (détection locale, bounding boxes sur 6 types d'artefacts locaux) et **HADM-G** (multi-label global, 12 catégories, binary cross-entropy). Backbone **ViTDet + EVA-02 (large)** avec tête Cascade-RCNN. Entraîné sur le dataset HAD : **37 554 images et 84 852 instances annotées** issues de SDXL, DALL-E 2/3 et Midjourney. Généralise à des générateurs non vus. Fournit un score de confiance par boîte → **directement utilisable comme seuil de rejet dataset**. Point clé pour votre cas : le tableau AP50 de HADM-L confirme la spécificité mains/pieds (**hand 74,5 / feet 47,3 AP50** vs torso 27,6, moyenne globale 43,3), c'est-à-dire que le détecteur est nettement meilleur sur les mains/pieds — exactement vos zones critiques (FootSegNet/HandSegNet). C'est le détecteur le plus proche de votre besoin.
- **DiffDoctor** — "Diagnosing Image Diffusion Models Before Treating", Yiyang Wang et al., ICCV 2025, arXiv 2501.12382. Code : github.com/ali-vilab/DiffDoctor. Détecteur d'artefacts **pixel-wise** (backbone **SegFormer-b5**) : selon le papier, *« we collect a dataset of over 1M flawed synthesized images and set up an efficient human-in-the-loop annotation process »*. Produit des **cartes de confiance d'artefacts par pixel** (valeur = probabilité d'artefact). Conçu pour donner un feedback de fine-tuning, mais le détecteur seul sert de scoring/localisation. Plus fin que HADM (pixel vs boîte).
- **HandRefiner** (ACM MM 2024, arXiv 2311.17957, code github.com/wenquanlu/HandRefiner) et **HandCraft** (arXiv 2403.01693) : détection+correction de mains malformées via inpainting conditionné ControlNet sur mesh de main. HandCraft fournit aussi le dataset **MalHand**. **3D Hand Mesh-Guided refinement** (arXiv 2506.12680, juin 2025) améliore avec un estimateur de mesh 3D SOTA. Ces méthodes *corrigent* ; leur module de détection sert de filtre.
- **"Detecting and Restoring Non-Standard Hands"** (arXiv 2312.04236) : détecteur **YOLOv8** fine-tuné classifiant mains standard/non-standard (Precision/Recall rapportés 0,85/0,90/0,95 sur 2006 images de test) + MediaPipe pour le squelette. Approche très légère.
- **ArtifactLens** (arXiv 2602.09475, 2026) : approche VLM ("Hundreds of Labels Are Enough") qui note les artefacts ; s'appuie conceptuellement sur votre grounding VLM Qwen2.5-VL déjà en place. Note que HADM et AHD sont les seuls détecteurs objet SOTA à poids publics ; SynArtifact et AbHuman n'ont pas publié leurs détecteurs.

**Compatibilité 16 Go :** ViTDet-EVA02-large et SegFormer-b5 sont des modèles de détection/segmentation qui tiennent confortablement en inférence sur une carte 16 Go (bien plus légers qu'un modèle vidéo). YOLOv8 + MediaPipe est trivial. **Verdict : l'axe le plus facilement prototypable.**

### Axe 2 — Stabilisateur temporel de lineart ("anti-line-boiling")

**État de maturité 2026 : gap réel.** Recherche approfondie (y compris via sous-agent dédié) : **il n'existe aucun modèle publié dont la tâche explicite soit de prendre une séquence de lineart raster tremblante et de produire une séquence de lineart stabilisée.** Les méthodes de deflickering vidéo génériques (Deep Video Prior arXiv 2010.11838 ; "Blind Video Deflickering by Neural Filtering with a Flawed Atlas", CVPR 2023) ne sont pas spécifiques au lineart. Les méthodes de colorisation temporelle que vous avez déjà identifiées (LVCD arXiv 2409.12960, AniDoc CVPR 2025, AnimeColor arXiv 2507.20158) stabilisent la couleur, pas les lignes. Quatre contournements existent, tous imparfaits :

- **Reformulation vectorielle (élimine le boil par construction).** **Sketch Video Synthesis** (arXiv 2311.15306, nov. 2023, Eurographics/CGF 2024, projet sketchvideo.github.io) convertit une vidéo en SVG Bézier frame-par-frame avec une **perte de cohérence temporelle** basée sur un Neural Layered Atlas + init cross-frame de strokes. **Breathing Life Into Sketches / Live Sketch** (arXiv 2311.13608, CVPR 2024, livesketch.github.io) anime un SVG unique en décomposant le mouvement en déformations locales de strokes + transformations affines globales — pas de boil car les mêmes strokes sont transformées, pas régénérées. Travaux 2025 : "differentiable motion trajectories" (arXiv 2509.25857), "Multi-Object Sketch Animation" (arXiv 2508.15535), FlipSketch (arXiv 2411.10818), SwiftSketch (SIGGRAPH 2025, vectoriseur rapide par diffusion). **Limite : prototypes optimisation-based lents, sujets simples.**
- **Inbetweening géométrique (préserve la topologie des lignes).** **AnimeInbet** — "Deep Geometrized Cartoon Line Inbetweening", Siyao et al., ICCV 2023, arXiv 2309.16643, code+dataset (MixamoLine240) github.com/lisiyao21/AnimeInbet. Géométrise le lineart raster en graphes d'endpoints et traite l'inbetweening comme fusion de graphes + repositionnement de sommets → **préserve la topologie des lignes** (évite le flou de RIFE/FILM). **LayerInbetween** (ACM TOG 2025, DOI 10.1145/3811364) ajoute la gestion des occlusions/layering. Code léger, plausiblement 16 Go (non confirmé).
- **ControlNet lineart + module temporel (de-facto communautaire, mais orienté rendu).** Consensus des workflows ComfyUI/Civitai : lineart ControlNet (jugé "équilibré" pour guider/réduire le flicker) empilé avec softedge/reference_only + **TemporalNet** (strength faible) + AnimateDiff/Prompt Travel ou Deforum. mmagic (open-mmlab) documente "ControlNet + multi-frame rendering" pour "éviter le scintillement". **temporal-controlnet-lineart-svd-v1** (CiaraRowles, HuggingFace, code github.com/CiaraStrawberry/sdv_controlnet) : ControlNet temporel sur base SVD piloté par lineart. **Ces pipelines stabilisent le rendu final, pas la couche de lignes en tant que telle.**
- **Extraction de lineart vidéo (per-frame, PAS temporellement stable).** **AniLines** (github.com/zhenglinpan/AniLines-Anime-Lineart-Extractor, MIT, 2025) extrait le lineart d'images ET vidéos, modes detail/basic, fp16 (jusqu'à 5× plus rapide, testé 1080p). **Mais : extracteur per-frame sans module temporel → boil quand appliqué image par image.** Idem Anime2Sketch, SketchKeras, General Virtual Sketching (TOG 2021).

**Comparaison à votre existant :** votre guide 3D Blender (proxy metaball piloté MediaPipe) est en réalité **votre meilleure défense actuelle contre le line boiling** — un guide 3D cohérent frame-à-frame donne un ControlNet/pose stable, ce qui est conceptuellement supérieur à re-générer chaque frame indépendamment. La piste la plus prometteuse serait de coupler votre guide Blender à AnimeInbet (topologie) ou à une reformulation vectorielle. **Verdict : axe hors de portée pour un prototype production court terme ; prototype de recherche seulement.**

### Axe 3 — "ColorLock" / cohérence de palette de personnage

**État de maturité 2026 : partiellement mûr, briques combinables, pas de solution clé-en-main.**

- **Conditionnement à la génération : Palette-Adapter / "Palette Aligned Image Diffusion"** (Aharoni, Porat, Lischinski, Shamir ; arXiv 2509.02000). Conditionne un modèle text-to-image sur une palette utilisateur interprétée comme **histogramme de couleurs épars**, avec deux paramètres scalaires (entropie d'histogramme, ratio palette-vers-histogramme) contrôlant la stricte adhérence. C'est le travail le plus formel prouvant qu'un modèle de diffusion peut internaliser des contraintes de couleur dures. Précurseur : Vavilala et al. (2023) concaténait l'info palette en entrée (contrôle grossier).
- **Correction post-génération : wavelet color correction (training-free).** Documentée comme module qui résout le décalage global de schéma colorimétrique des modèles de diffusion (3DEnhancer arXiv 2412.18565 rapporte PSNR/SSIM améliorés en l'appliquant au baseline). Léger, sans entraînement, applicable en post-traitement — **le candidat idéal pour une correction de dérive chromatique frame-à-frame** dans votre pipeline.
- **Inference-time loss-guided colour preservation** (arXiv 2601.17259, 2026) : technique de préservation de couleur guidée par perte au moment de l'échantillonnage. Confirme que "les systèmes actuels gèrent bien mieux les conditions spatiales/structurelles que les conditions de couleur précises" (survey Pu et al.) — donc la couleur reste un point dur.
- **Pratique communautaire (2026)** : le "color palette locking" est cité comme essentiel en pixel art (verrouillage de 24 couleurs, cf. études de cas 2026), mais reste à ~80-90 % de cohérence avec IP-Adapter et ~15-20 % de dérive résiduelle sur les générations "lockées".

**Comparaison à votre existant :** vous couvrez déjà la cohérence de *forme* (IP-Adapter/LoRA de personnage). La couleur est orthogonale. Le combo recommandé : palette de référence extraite du character sheet → wavelet color correction en post par frame (training-free, léger) + éventuellement Palette-Adapter à la génération. Tient largement en 16 Go. **Verdict : prototypable, deuxième priorité après le QC anatomique.**

### Axe 5 — DesignLock / conformité au design canonique

**État de maturité 2026 : mûr conceptuellement, pattern standardisé.** Au-delà de votre étude de cas interne LoRA Jordan AJ1 (non publiée pour raisons d'IP Nike), la vérification automatique de fidélité topologique à un design de référence est devenue un pattern courant dans la littérature 2026, principalement via **features de foundation models (DINO) + matching géométrique** :

- **Vérification de fidélité d'objet par DINO + matching bipartite** — **VIGIL** ("Tackling Hallucination Detection in Image Recontextualization", arXiv 2602.14633, 2026) : pour chaque objet segmenté, embeddings **DINOv3-ViT-B/16** ; matrice de similarité cosinus + **Linear Sum Assignment** (matching bipartite) restreint aux paires de même classe (labels **SAM3**) ; une paire non appariée = hallucination "object omission". Les paires validées repassent au VLM (**Qwen3-VL-8B-Instruct**) pour détecter "object mutation" / "reference bleeding". **C'est presque exactement le "DesignLock" générique que vous décrivez — et il réutilise SAM + un VLM local, vos deux briques existantes.**
- **Métriques de fidélité sujet standardisées** — **HECTOR** (arXiv 2603.08850) : CLIP-I (identité sémantique) + DINO-I / DINOv2 (structure/textures fines), plus versions régionales R-CLIP/R-DINO croppées sur bounding box. **DivRL** (arXiv 2606.23950) définit **sDINO (Structural DINO)** = moyenne des max de similarité cosinus patch-à-patch, et **si-IoU** (Scale-Invariant IoU) qui découple taille/position pour comparer la forme des masques. **Visual-Aware CoT** (arXiv 2512.19686) : GroundingDINO localise, puis similarité de features DINO sur crops pour scorer la cohérence d'identité.
- **Fondement** : "A Tale of Two Features" (sd-complements-dino.github.io) montre que les features DINOv2 donnent des correspondances éparses mais précises, complémentaires à SD. DINOv3 (2025) améliore les features denses pour la localisation fine.

**Comparaison à votre existant :** votre SAM fine-tuné segmente déjà les composants (mains, pieds). Le "DesignLock" générique = SAM (segmentation composants) → DINOv2/v3 (embeddings par composant) → matching bipartite vs référence + comptage de composants → seuil de similarité, avec le VLM Qwen pour le raisonnement sur mutations. **Toutes les briques sont déjà dans votre stack.** si-IoU vérifie les proportions ; le comptage de composants appariés vérifie le "nombre de composants distinctifs". **Verdict : le deuxième axe le plus directement prototypable, avec un chevauchement maximal avec l'existant.**

### Axe 6 — Comparaison globale et priorisation

**Ce que fait déjà votre pipeline :** SAM fine-tuné (segmentation qualité de parties du corps), ControlNet OpenPose/Lineart (contrôle structurel), guide 3D Blender proxy metaball piloté MediaPipe (pose), dataset synthétique wildcards+SDXL (fabricatedXL_v70 / Illustrious), grounding VLM Qwen2.5-VL:7b local.

**Positionnement conceptuel de chaque axe :**
- **QC anatomique (HADM/DiffDoctor)** : couche *aval* de contrôle qualité, complémentaire (pas concurrente) de vos LoRA anti-mains *amont*. Ferme la boucle "générer → filtrer → intégrer au dataset". Réutilise le paradigme détection que vous maîtrisez déjà via SAM. Le fort AP50 de HADM-L sur mains/pieds recoupe précisément vos FootSegNet/HandSegNet.
- **DesignLock (SAM+DINO+matching)** : extension directe de votre SAM + VLM. Ajoute la couche "comparaison à une référence canonique" que ControlNet (structurel générique) ne fournit pas.
- **ColorLock (wavelet correction + Palette-Adapter)** : orthogonal à IP-Adapter (forme). Comble un axe couleur non couvert.
- **Lineart temporel** : conceptuellement, votre guide 3D Blender est déjà une meilleure parade au boil que la génération frame-indépendante. Les vraies alternatives (AnimeInbet, vectorisation) sont des prototypes.
- **Outils vidéo** : MatAnyone et SeedVR2 s'insèrent en aval (matting/upscale) ; VACE 1.3B / AniSora / Wan 2.2 5B en génération ; RIFE en interpolation finale ; blender-mcp comme couche de pilotage LLM de votre guide 3D.

## Recommendations

**Étape 1 (0-4 semaines) — Prototyper le QC anatomique.** Déployer **HADM** (github.com/wangkaihong/HADM) sur une des deux cartes 16 Go comme filtre de dataset : rejeter automatiquement toute image générée dont HADM-L/HADM-G dépasse un seuil de confiance d'artefact. Comparer avec **DiffDoctor** (cartes pixel-wise, plus fin) sur un échantillon. Benchmark de bascule : si le taux de faux positifs sur votre style anime (Illustrious) dépasse ~15-20 %, fine-tuner le seuil ou ré-entraîner HADM-L sur un petit set annoté de votre style (HAD est majoritairement photoréaliste/SDXL — attention au domain gap anime, à valider explicitement).

**Étape 2 (1-2 mois) — Prototyper le DesignLock.** Chaîner SAM (déjà en place) → embeddings DINOv2/DINOv3 par composant → matching bipartite (Linear Sum Assignment) vs character sheet de référence + comptage de composants appariés + si-IoU pour les proportions, avec Qwen2.5-VL pour le raisonnement mutation/bleeding (pattern VIGIL, arXiv 2602.14633). Benchmark : viser une détection fiable des écarts de nombre de composants (ex. sneaker AJ1 : nombre d'œillets, présence du Swoosh) avant d'étendre aux proportions.

**Étape 3 (2-3 mois) — ColorLock léger.** Ajouter la **wavelet color correction** (training-free) en post-traitement par frame, palette de référence extraite du character sheet. Mesurer la dérive chromatique (ex. ΔE moyen sur zones de personnage) avant/après. Si insuffisant, évaluer Palette-Adapter (arXiv 2509.02000).

**Étape 4 (en parallèle, faible risque) — Intégrer les outils vidéo mûrs.** MatAnyone/MatAnyone2 (matting temporel, s'appuie sur votre SAM), SeedVR2 3B via BlockSwap (upscale, rester en batch_size 1 sur 16 Go si pas de cohérence temporelle nécessaire, sinon batch 5 sur la RTX 5080), RIFE v4.x anime (interpolation finale). Piloter le guide 3D Blender via **blender-open-mcp** (Ollama, aligné sur votre stack).

**Étape 5 (recherche, ne pas prioriser en production) — Lineart temporel.** Traiter comme R&D exploratoire. Tester AnimeInbet (github.com/lisiyao21/AnimeInbet) sur des paires de keyframes lineart issues de votre guide Blender. Ne pas attendre de qualité production. Réévaluer si un modèle "lineart deflicker" dédié apparaît.

**Seuils qui changeraient les priorités :** (a) si vous ajoutez une carte 24 Go+ ou un accès cloud ponctuel → VACE-Fun-A14B (≥80 Go officiel), ToonComposer (~57 Go pour 480p/61 frames) et Wan 2.2 A14B deviennent envisageables pour l'inbetweening/colorisation unifiés ; (b) si AniSora V3.2 (Wan 2.2, 8 steps) atteint votre barre qualité anime après vos tests → il devient le générateur vidéo de référence ; (c) si un modèle lineart-deflicker dédié est publié → reprioriser l'axe 2.

## Caveats

- **Domain gap anime non résolu par les sources.** HADM/DiffDoctor/HandRefiner sont entraînés majoritairement sur SDXL photoréaliste, DALL-E, Midjourney (HAD = 37 554 images / 84 852 instances de ces générateurs). Leur transfert au style anime Illustrious (fabricatedXL_v70) n'est **pas** documenté dans les sources trouvées — à valider empiriquement avant toute mise en production. C'est le principal risque de l'étape 1.
- **Chiffres VRAM à prendre avec prudence.** Les figures 16 Go pour SeedVR2 (BlockSwap), VACE 1.3B, AniSora 12 Go proviennent souvent de docs communautaires/tutoriels (RunComfy, seedvr2.net, Will It Run AI) avec marge ±1-2 Go annoncée. Pour Wan 2.2 TI2V-5B en particulier, la carte HF officielle Wan-AI cite « at least 24GB » alors que la communauté annonce 8-12 Go avec offload : les deux sont vrais selon le niveau d'offload/résolution. Les prototypes de recherche (Sketch Video Synthesis, AnimeInbet, TLB-VFI, VidSketch) n'ont **pas** de chiffres VRAM publiés fiables ; leur faisabilité 16 Go est une inférence, pas une donnée mesurée.
- **Lineart temporel : gap confirmé, pas d'extrapolation.** J'affirme explicitement qu'aucune source fiable ne décrit un modèle "lineart deflicker" dédié en 2026. Les tools consumer (LensGo, PixAI v4.0, CapCut) sont rapportés (sources marketing/blog, non benchmarkées) comme souffrant encore de line boiling — indice anecdotique que le problème reste ouvert.
- **AniSora V3.2 qualité anime.** Un seul retour utilisateur (HuggingFace discussion) juge la qualité "insuffisante" pour l'anime ; ce n'est pas un benchmark. À tester directement.
- **VACE nomenclature.** "VACE" désigne officiellement "Video All-in-one Creation and Editing" (Tongyi Lab/Alibaba) ; les variantes "Composable/Aware Editing" sont des gloses communautaires. Le support Wan 2.2 est via modules "Fun VACE" expérimentaux, pas encore un VACE 2.2 officiel stabilisé au moment de l'audit.
- **Sources datées post-juillet 2026.** Certaines pages citées (ex. arXiv 2602.*, 2603.*, 2606.*) portent des identifiants de 2026 cohérents avec la date de l'audit ; je les ai retenues pour le pattern technique (DINO+matching, VLM scoring) qui est stable, mais les numéros exacts de version/dataset de ces preprints très récents doivent être revérifiés.
