**RÉCIDIVE PUIS CORRECTIF DÉFINITIF (2026-08-02 soir → 2026-08-03 matin)** :
le 2e lancement (celui décrit juste en dessous, relancé 18:21) a reproduit
**exactement le même mur** vers step ~1077-1151/4438 -- confirmé par
l'utilisateur en direct (`power.draw` ~77-80W, température ~45°C, signature
identique à la 1ère fois). Un simple redémarrage ne suffisait donc pas ;

Diagnostic approfondi (log `[mem] step=N allocated_mb=X reserved_mb=Y`
ajouté à chaque step) : `allocated` restait stable (~3.79 Go) pendant que
`reserved` doublait en 2-3 steps -- fragmentation d'allocateur confirmée,
pas une fuite réelle. Cause racine : `PYTORCH_ALLOC_CONF` contenait
`expandable_segments:True`, **silencieusement ignoré sous Windows**
(`UserWarning: expandable_segments not supported on this platform`, vérifié
explicitement -- torch 2.10.0+cu130 sur cette machine) depuis le tout début,
donc la mitigation censée exister n'avait jamais été active. Un premier
correctif (`max_split_size_mb:256` + séquence max réduite à 2048) a été
testé en smoke test et s'est avéré **contre-productif** (dégradation dès
step ~20 au lieu de ~1100). Correctif final retenu, validé par smoke test
(50/50 steps stables) puis par ce 3e run complet (stable de step 20 à 4164+,
`reserved` oscillant 4.2-4.9 Go, jamais de dérive) :
1. `PYTORCH_ALLOC_CONF` limité à `garbage_collection_threshold:0.8` (seule
   clé confirmée active sous Windows sur cette machine).
2. `group_by_length=True` (bucket par longueur similaire via
   `LengthGroupedSampler` de HF) -- le vrai levier : la variance de longueur
   de séquence (code source brut, 200-8000 caractères, pas de packing) était
   la cause structurelle, pas juste un besoin de nettoyer plus souvent.
3. Callback `PeriodicCacheClearCallback` (`gc.collect()` +
   `torch.cuda.empty_cache()` à chaque step) en filet de sécurité, non
   dépendant d'un réglage d'allocateur spécifique à la plateforme.
Confirmation croisée : la doc TRL (reducing_memory_usage) relie le mode
"padding-free" auto-activé par Unsloth à FlashAttention 2 pour un bénéfice
mémoire optimal -- FA2 est indisponible sur ce setup Windows (`FA2 = False`),
ce qui explique pourquoi le mode padding-free seul ne suffisait pas à
absorber la variance de longueur. Détails complets dans le docstring de
`train_stage1_thestack.py`. Voir aussi la mémoire
`windows-detached-training-pitfalls.md`.

## Suite -- 2026-08-02 (Claude Code, même journée) : déploiement Ollama + RAG

Priorité de reprise donnée par l'utilisateur : "finaliser le LLM local
codeur/assistant en inférence sur RTX 5060 Ti". Trois sous-tâches traitées :

1. **Stage 2 → Ollama, confirmé exploitable.** L'adaptateur n'avait jamais
   été testé hors transformers/PEFT. Pipeline complet exécuté :
   - Pinning Ollama corrigé -- **nouveau piège trouvé, distinct de ceux déjà
     documentés** : `ollama app.exe` (le tray Windows, auto-démarré via
     `Startup\Ollama.lnk`) gère son propre `ollama serve` indépendamment de
     `launch_ollama.bat`, avec `OLLAMA_MODELS` par défaut
     (`~/.ollama/models`, vide) et sans aucun pinning GPU/Vulkan. Il faut
     tuer `ollama app.exe` ET `ollama.exe` puis relancer via
     `launch_ollama.bat` -- **revalidé à chaque redémarrage Windows**, le
     raccourci Startup relance l'app par défaut. Pas désactivé (décision
     laissée à l'utilisateur, changement système hors périmètre).
   - Fusion LoRA→base fp16 (CPU, script `merge_stage2_fp16.py` ad hoc,
     transformers+peft purs, pas unsloth -- évite la dépendance CUDA/bnb
     pour cette étape) : `.../stage2_instructions_v2/merged_fp16/` (~8 Go,
     non versionné, gitignoré via `workspace/qlora_dataset/training_stage2/`).
   - Conversion GGUF fp16 via `convert_hf_to_gguf.py` (script Python pur du
     clone llama.cpp de `.unsloth/`, aucune compilation nécessaire) :
     `.../stage2_instructions_v2/gguf/ov3rlord-coder-stage2v2-f16.gguf`.
   - **Pas de quantisation possible** : aucun compilateur C++ sur la machine
     (`cl.exe`/`cmake`/`ninja`/`nvcc` absents), donc pas de
     `llama-quantize.exe`. Modèle servi en fp16 (8.1 Go) -- tient
     confortablement sur les 16 Go de la RTX 5060 Ti avec `num_ctx=32768`.
     **Note pour la suite : installer Visual Studio Build Tools + CUDA

     différer cet investissement pour l'instant (fp16 = "test, pas encore
