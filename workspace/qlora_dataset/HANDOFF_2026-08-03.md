# Handoff -- 2026-08-03, RAG semantique local pour le LLM de secours

Suite directe de `HANDOFF_2026-08-02.md`, section "RAG factuel esquissé, pas
un vrai RAG sémantique" (point 2). Ce jour-là, seul un catalogue de
chargement manuel avait été mis en place (`DOCS/RAG_SOURCES.md` +
`.aider.conf.yml`) -- pas de recherche automatique par pertinence. Tâche du
jour : construire ce mécanisme de recherche réel, demandée via
`RGA sémantique.txt` (Bureau).

## Ce qui est fait

- **`agents/infra/rag_indexer.py`** -- indexe les sources listées dans
  `DOCS/RAG_SOURCES.md` (CLAUDE.md, DOCS/INDEX.md, DOCS/LLM-Secour.md,
  RAPPORT_AUDIT_PIPELINE_AOUT2026.md, RAPPORT_IDEES_HISTORIQUE_V150_V227.md,
  5 rapports de veille `DOCS/MD/`). Découpage par **unité logique** (chaque
  item de liste `- `/`* `/`1. ` devient son propre chunk au lieu d'être noyé
  dans un paragraphe de 10+ puces sans rapport) puis empaquetage jusqu'à
  ~900 caractères. Persisté dans `workspace/rag_index/` (`embeddings.npy`,
  `chunks.jsonl`, `manifest.json` avec hash SHA256 par source pour détecter
  un changement). CPU uniquement, aucune carte GPU sollicitée.
  `py -3.12 agents/infra/rag_indexer.py --status` affiche l'état sans
  reconstruire.
- **`agents/infra/rag_query.py`** -- recherche **hybride** : similarité
  cosinus (embeddings sentence-transformers) fusionnée par rang (RRF,
  constante k=60) avec un score BM25 lexical (`rank_bm25`). CLI :
  `py -3.12 agents/infra/rag_query.py "question" [--top-k N] [--json]`.
  Importable : `from agents.infra.rag_query import retrieve, format_context`.
  Lève `RagIndexMissing` si l'index n'existe pas -- capturée par l'appelant
  pour ne jamais bloquer (voir plus bas).
- **Modèle retenu : `intfloat/multilingual-e5-small`** (pas
  `all-MiniLM-L6-v2`, testé en premier). Corpus majoritairement francophone
  -- le modèle anglais donnait un classement nettement moins cohérent sur
  des questions en français (vérifié empiriquement, voir "Limite connue"
  ci-dessous).
- **Hybride BM25 nécessaire, pas un luxe** : la similarité cosinus seule
  souffrait d'un effet de "hub" -- des passages longs et génériques
  (rapports de veille) dominaient systématiquement le classement face à des
  identifiants techniques rares et courts (`dpmpp_2m`, `taesdxl`, présents
  dans une puce ADR de CLAUDE.md). Diagnostiqué en comparant le score d'une
  requête hors-sujet ("recette de gâteau au chocolat") : quasi identique
  (0.82-0.83) au score d'une requête pertinente (0.82-0.86) -- l'embedding
  seul ne discriminait presque pas sur ce corpus/modèle. L'ajout BM25 (RRF)
  corrige ce cas pour les requêtes qui partagent des mots-clés avec la
  réponse.
- **Intégration `agents/creative/llm_router.py`** (fichier réel post-réorg,
  voir note ci-dessous) : `call()` précède désormais automatiquement le
  `system` prompt d'un bloc "Contexte projet pertinent" (top-3 passages,
  500 caractères max chacun) avant chaque appel LLM (local Ollama ou GLM).
  Fonction `_with_rag_context()` -- capture toute exception (import RAG
  absent, index manquant, échec du modèle) et retombe silencieusement sur le
  `system` original, conformément à ADR-009 (jamais de blocage du routage
  LLM pour une dépendance annexe). Testé directement (import + appel de
  `_with_rag_context`), **pas testé end-to-end via un vrai appel Ollama**
  (`ollama serve` non lancé pendant cette session -- à vérifier en usage
  réel).
- **`requirements.txt`** : ajout `sentence-transformers<4.0` (la 5.x tire
  `torchcodec`, qui exige des DLL FFmpeg absentes sur cette machine --
  inutile de toute façon pour de l'embedding texte seul) et `rank_bm25`
  (pur Python, aucune dépendance GPU/lourde).
- **CLAUDE.md** : nouvelle section "Lancement de process détachés
  (entraînements longs)" -- convention `start cmd /k py -3.12 <script>`
  pour les prochains entraînements détachés depuis une session Claude Code,
  à la place de PowerShell `Start-Process` (fenêtre cachée par défaut,
  aucune progression visible sans rediriger vers un log).

## Limite connue -- à ajouter à un futur `LIMITATIONS_CONNUES.md` RAG si le sujet revient

**Angle mort cross-lingue confirmé** : une question posée en français dont
la seule réponse correcte est un passage anglais (ex. "quel sampler et
quel VAE par défaut ?" en français, réponse dans la puce ADR-002/ADR-003 de
CLAUDE.md, écrite en anglais) **n'est pas bien retrouvée** -- le chunk
correct est sorti classé ~68e/268 sur les tests. BM25 ne peut pas combler
cet écart (aucun mot-clé partagé entre "defaut"/"sampler" en français et
"default"/"sampler" en anglais côté texte source), et la similarité
sémantique seule (e5 multilingue) n'est pas assez fine sur ce corpus
restreint pour compenser entièrement. **Reformuler la question dans la
langue du document cible contourne le problème** (vérifié : la même
question en anglais retrouve le bon passage en position #1). Piste non
explorée : reformuler systématiquement la requête dans les deux langues
avant recherche (double retrieve + fusion), pas fait cette session (retour
sur investissement incertain vu la taille du corpus).

## Ce qui reste ouvert

1. **Test end-to-end réel non fait** : `_with_rag_context()` est vérifiée
   unitairement, mais aucun appel `agents/creative/llm_router.py::call()`
   n'a été fait avec Ollama réellement démarré pendant cette session (pas
   lancé, pour rester conforme à la consigne "CPU uniquement, GPU non
   touchées" -- Ollama tourne normalement sur la RTX 5060 Ti). À vérifier
   à la prochaine session où Ollama est actif : lancer `call("general", "...")`
   et confirmer que le contexte RAG apparaît bien dans le prompt final
   envoyé au modèle (activer `logging.DEBUG` sur le logger `llm_router`).
2. **Intégration `llm_router.py` non commitée intentionnellement.** Le code
   réel vit maintenant dans `agents/creative/llm_router.py`, qui est un
   fichier **non suivi par git** (issu de la grosse réorganisation
   `agents/*.py` documentée comme non committée dans
   `HANDOFF_2026-08-02.md`, "hors périmètre... à committer ou nettoyer par
   l'utilisateur"). Mélanger mon intégration RAG avec cette réorg dans un
   seul commit aurait violé la consigne "commit isolé" de cette tâche --
   j'ai donc laissé cette intégration en modification non committée dans
   l'arbre de travail (fonctionnelle, testée, juste pas dans l'historique
   git). **Décision à prendre** : soit committer la réorg complète (portée
   bien plus large, décision de l'utilisateur), soit me demander de recréer
   l'intégration isolément sur `agents/llm_router.py` tel qu'il est
   actuellement committé (le fichier réel avant réorg) si la réorg ne doit
   finalement pas être committée bientôt.
3. **`DOCS/RAG_SOURCES.md` reste la seule liste de vérité pour
   `SOURCES` dans `rag_indexer.py`** -- toujours pas de lecture automatique
   du tableau markdown (même limite déjà documentée dans ce fichier avant
   cette session) : si un nouveau rapport est ajouté à `DOCS/MD/`, il faut
   l'ajouter manuellement aux deux endroits (le tableau ET la liste
   `SOURCES`).
4. **Pas de détection automatique de staleness** : `manifest.json` contient
   un hash par source, mais rien ne compare ce hash au fichier courant pour
   déclencher un rebuild automatique -- reconstruire manuellement
   (`py -3.12 agents/infra/rag_indexer.py`) après toute modification d'une
   source indexée (fait manuellement cette session après l'ajout de la
   section CLAUDE.md).

### Ce qui est fait

- **`workspace/qlora_dataset/scripts/build_source_commitpack_full_python.py`**
  (committé, isolé -- voir commit de cette session). Nom volontairement
  distinct de l'existant (`_full_`) pour ne jamais écraser
  `dataset_source_commitpack_python.jsonl`, cohérent avec la règle
  CLAUDE.md "un nouveau run ne doit jamais écrire dans le dossier de
  sortie d'un run existant sans confirmation explicite", appliquée ici à
  un fichier de données source plutôt qu'un run d'entraînement.
- **Aucun cap artificiel sur le filtrage** (contrairement à toutes les
  autres sources, cible fixe choisie à l'avance) -- le volume est décidé
  par les filtres de qualité ; sous-échantillonnage seulement si le
  résultat dépasse 150 000, et alors par diversité de type de commit
  (classification heuristique feat/fix/refactor/perf/other, CommitPack n'a
  pas de champ structuré) plutôt que par troncature aux X premiers lus
  (biaisée par l'ordre des shards).
- **Architecture bornée en mémoire sur un corpus de 223 Go** : un worker
  par shard (multiprocessing, 8/12 coeurs logiques -- 4 laissés libres
  pour ne pas affamer le Stage1 TheStack alors en cours), chaque worker
  écrit directement son résultat filtré sur disque (jamais gardé en RAM
  dans le process principal, seuls des compteurs remontent) ; le
  sous-échantillonnage final utilise un tirage par réservoir (Algorithme
  R, non biaisé) par type de commit sur les fichiers déjà filtrés (donc
  petits, passe supplémentaire bon marché).
- **Validé par smoke test avant le run complet** : filtrage correct sur un
  échantillon réel de 5000 lignes (312 lignes/s mono-processus, taux de
  rétention et classification cohérents), ce qui a aussi permis d'estimer
  la durée totale avant de lancer le run de 223 Go.
- **Run complet lancé** via `start cmd /k py -3.12 ...` (fenêtre visible,
  convention CLAUDE.md), suivi via un log structuré séparé
  (`E:\data\commitpack_full_python_subset\filter_log.txt`) plutôt que la
  fenêtre cmd elle-même (bruitée par des `SyntaxWarning: invalid escape
  sequence` -- attendu et inoffensif, `ast.parse()` sur du code tiers
  ancien utilisant des chaînes non-raw comme regex, ne fait pas échouer le
  parsing).
